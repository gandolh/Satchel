# Task 10: Go live

## Context

Phase 1 is built and tested locally. This brief makes it deployable and
writes down every owner step, in order, with exact commands. Deploying,
registering Satchel in production Ward, writing secrets, `npm link` and
editing `~/.claude/CLAUDE.md` are owner steps; the agent prepares them and
hands them over.

How vps-deploy works now: every service is a rootless Docker container built
on the VPS from `infrastructure/Dockerfile` and
`infrastructure/docker-compose.yml` in the source repo, published on
loopback; there is no pm2 (`../vps-deploy/README.md`, "Services are
containers"). Templates: `../wzd_auth/infrastructure/Dockerfile` (it also
builds better-sqlite3 on node:24-alpine) and
`../sports-app/infrastructure/docker-compose.yml`; the stack template is
`../vps-deploy/stacks/sports-app.ts`. The summary is the Deploy and "Changes
in other repos" sections of [architecture.md](../../wiki/architecture.md).

Check [open-questions.md](../../wiki/open-questions.md) for the name first:
renaming is cheapest before this brief.

`../vps-deploy/secrets/` (the owner writes `satchel.env`). Any other stack.

## What to do

1. **Dockerfile**, multi-stage like Ward's: a deps stage with the native
   toolchain, a builder that compiles `shared` and `server`, a proddeps stage
   with `npm ci --omit=dev -w @satchel/server --include-workspace-root`, and a
   node:24-alpine runtime holding `server/dist`, `shared/dist` and the
   production `node_modules`. `HOST=0.0.0.0`, `PORT=8795`, `DATA_DIR=/data`.
   Keep Ward's comment on why the container runs as uid 0 under rootless
   Docker with a bind-mounted `/data`.
2. **docker-compose.yml**, like sports-app's: service and image
   `satchel-api`, ports `127.0.0.1:${SATCHEL_PORT:-8795}:${SATCHEL_PORT:-8795}`
   (loopback only, with the same warning comment), `env_file: .env`, `/data`
   bind-mounted from `${SATCHEL_DATA_DIR:-../data}`, `restart:
   unless-stopped`, and a healthcheck on `/api/health`.
3. **Local container check.** With a gitignored `infrastructure/.env` holding
   the local Ward trio, `docker compose -f infrastructure/docker-compose.yml
   up --build -d`; `curl http://127.0.0.1:8795/api/health`; post a message
   through the local dev web app pointed at it or through the store, `down`,
   `up`, and confirm the message survived.
4. **vps-deploy.** First `git status` in `../vps-deploy`; if any file you own
   there has uncommitted changes, stop and tell the owner. Then:
   - `../vps-deploy/lib/estate.ts`: `satchel: new SourceRepo(this, "satchel-repo", { path:
     "../satchel", workspaceRoot: true })`.
   - `../vps-deploy/stacks/satchel.ts`, modelled on sports-app's: `basePath: "/satchel"`,
     `apiPrefix: "/satchel-api"`, client `distDir: "web/dist"`, `remoteDir:
     "/var/www/satchel"`, `publicUrl: https://<domain>/satchel/`,
     `verifyAssetBase: true`, build `npm run build` with `baseEnv:
     "SATCHEL_BASE"`, `tryFiles: "spa"`; `persistentState` for
     `/srv/satchel-api/data`, excluding `/data`, `contains: "every Satchel
     message and Claude token hash"`; service `serverDir:
     "/srv/satchel-api"`, the compose file, service `satchel-api`, port
     8795, `DATA_DIR`, healthcheck `/api/health`, loopback required. Route
     notes saying `handle_path` strips `/satchel-api` so the service sees
     `/api/*` and `/claude/*`.
   - `../vps-deploy/app.ts`: construct the stack and add
     `satchel.useWard(ward.identityFor(satchel))` next to the others.
   - `node cli.ts synth`, then `node cli.ts --graph` to confirm port 8795 and
     both prefixes are unclaimed elsewhere. Run vps-deploy's own checks
     (`npm run typecheck` and `npm test` if present).
   - Commit the stack, estate, app and regenerated Caddyfile as one commit in
     vps-deploy.
5. **README "Owner setup"**, in this order, each with exact commands or
   clicks:
   1. In production Ward's console (`https://gandolh.ro/ward/console`, as the
      break-glass superuser): register app `satchel` / "Satchel" with public
      registration closed; issue a service key (shown once); grant your own
      account `admin` on `satchel`.
   2. Put the key in `~/projects/vps-deploy/secrets/satchel.env` as
      `WARD_APP_KEY=...`.
   3. Redeploy Ward's UI so its login allowlist knows `/satchel/` (brief 04
      added it): `cd ~/projects/vps-deploy && node cli.ts ward deploy`.
   4. `cd ~/projects/vps-deploy && node cli.ts satchel all`.
   5. Open `https://gandolh.ro/satchel/` on the phone, sign in, Add to Home
      Screen.
   6. Settings → Connect Claude → Create token. Then
      `mkdir -p ~/.config/satchel && umask 077 && printf 'SATCHEL_TOKEN=%s\n'
      '<paste>' > ~/.config/satchel/env`.
   7. `cd ~/projects/satchel && npm run build && cd cli && npm link`, then
      `satchel unread` from any directory.
   8. Add this line to `~/.claude/CLAUDE.md`: "When the owner asks to check
      the inbox (or "my ideas", "Satchel"), run `satchel guide` and follow
      it."
   9. Write a message on the phone, then say "check my inbox" in Claude Code.
   Later updates: `node cli.ts satchel deploy` for the web app, `node cli.ts
   satchel server` for the API.

## Acceptance

- The image builds locally, the container answers `/api/health` on
  127.0.0.1:8795 only, and data survives `down`/`up`.
- `node cli.ts synth` succeeds and the regenerated Caddyfile has
  `handle_path /satchel-api/*` → `localhost:8795` and the `/satchel` static
  route; vps-deploy's checks pass.
- The README's owner setup is complete enough to follow without this brief.
- Nothing was deployed, no secret was written, `npm link` was not run, and
  `~/.claude/CLAUDE.md` was not edited.
